# APP (Automatic Project Proposal)

> 제안요청서(RFP) PDF를 올리면 요구사항과 평가 기준을 분석하고, 제안의 축(Win Theme)을 골라
> 제안 발표자료(.pptx)를 만들어 주는 도구.
> 사업에 관한 내용은 전부 RFP에서 나오고, 사용자가 입력하는 것은 제안사(우리 회사) 정보뿐입니다.

</br>

## 전체 사용 흐름

```
홈 화면
  └▶ 시작하기
      └▶ RFP 업로드 (PDF)
          └▶ RFP 분석 결과 + 전략 브리프 확인 · 반영할 요구사항 선택
              └▶ Win Theme 선택 · 직접 수정
                  └▶ 제안사 정보 입력 (회사명 · 소개 · 실적 · 로고)
                      └▶ 생성 중
                          └▶ PPTX 파일 자동 다운로드
```

`src/app/page.tsx`가 `step` 상태(`home` → `upload` → `analysis` → `wintheme` → `form` → `loading` → `done`)로
화면 전환을 관리합니다. 제안서는 항상 특정 RFP에 대한 응답이므로, 분석 결과 없이는 다음 단계로 갈 수 없습니다.

`AppShell.tsx`의 상단 바가 5단계(RFP 업로드 · Win Theme · 제안서 작성 · 문서 생성 · 다운로드)를 표시합니다.
좌측 사이드바는 없습니다.

</br>

## 핵심 기능

### 1. RFP PDF 텍스트 추출 (`lib/rfp/extractText.ts`)

`pdfjs-dist`로 **브라우저 안에서** PDF를 파싱합니다. 파일이 서버로 전송되지 않는 것이 이 설계의 의도입니다.
`pdfjs-dist`는 함수 내부에서 동적 import 하므로 이 모듈 자체는 SSR·빌드 타임에 안전합니다.

PDF에는 "줄"이나 "문장"이라는 개념이 없고 좌표가 찍힌 텍스트 조각만 있으므로, Y좌표가 비슷한 조각들을 묶고
X좌표 순으로 이어 붙여 줄 단위로 재구성합니다. 각 줄은 페이지 번호를 함께 보관하며, 이 번호가 나중에
제안서의 "근거 페이지"가 됩니다.

</br>

### 2. RFP 분석 (`lib/rfp/analyze.ts`)

규칙 기반 순수 함수입니다. 완벽하지 않으며, 사용자가 화면에서 눈으로 확인하고 취사선택하는 것을 전제로 한
**초안 추출**입니다.

- **제목 상태 기계**: `3. 요구사항 정의` / `Ⅳ. 제안서 평가 기준` 같은 제목을 만나면 이후 목록의 해석 문맥이
  바뀌고, 새로운 대제목에서 문맥을 벗어납니다. 공공 RFP가 즐겨 쓰는 **전각 로마숫자(Ⅰ~Ⅹ)** 와 번호 뒤
  공백이 없는 `2.성능 요구사항`도 제목으로 인식합니다.
- **요구사항**: 요구사항 문맥 안의 목록 항목이거나, 문맥과 무관하게 `~해야 한다 / 하여야 함 / 되어야 하며`
  같은 의무 표현을 가진 문장. 중복 텍스트는 제거합니다. 소제목에서 기능 / 비기능을 판정하며,
  **성능·보안·품질·가용성은 비기능**으로 분류합니다.
- **평가 기준**: `4.2 가격 평가: 20점`처럼 소제목이 배점을 갖는 경우와,
  **배점표 행**(`사업 이해도사업 목표및 요구사항 이해도10`)을 모두 수집합니다. 소계·합계 행은 제외합니다.
- **사업 개요**(`RfpMeta`): 사업명 · 발주기관 · 예산 · 기간 · 제출기한. 먼저 나온 값을 우선합니다
  (RFP는 앞부분에 요약 정보를 두는 것이 관례).

> **제출기한은 분석 화면에만 표시되고 PPTX에는 들어가지 않습니다.** `RfpSource`에 해당 필드가 없어서,
> 발표자료에는 사업명 · 발주기관 · 예산 · 기간만 전달됩니다.

#### 표로 된 RFP를 전제로 만들어졌습니다

공공 RFP는 표지의 사업 정보와 평가 배점을 대부분 **표**로 적습니다. PDF에서 표를 한 줄로 펼치면
셀 경계가 사라져서 아래 형태가 됩니다.

```
"사 업 명차세대 고객상담 AI 챗봇 시스템 구축"   ← 콜론 없음, 라벨 글자 사이가 벌어짐
"사업 이해도사업 목표및 요구사항 이해도10"       ← 배점에 "점"이 없음
```

그래서 라벨은 **공백을 제거한 문자열**로 찾고, 소비한 글자 수만큼 원문을 건너뛰어 값을 떼어냅니다.
배점은 `10점`뿐 아니라 줄 끝의 맨 숫자도 인식합니다. `항목: 값`이나 `30점`만 가정하면 이런 문서에서
아무것도 찾지 못합니다.

한편 `※`는 한국어 문서에서 각주 표시라 목록 기호에서 제외했습니다. 포함하면 배점 각주
(`※ … 85%(68점) 미만 …`)가 평가 항목으로 잡힙니다.

</br>

### 3. 전략 브리프 (`lib/rfp/strategy.ts`)

분석 결과를 제안 작성용 기초 데이터로 한 번 더 가공합니다. `StrategyBrief`가 담는 것:

| 필드 | 내용 |
|------|------|
| `compliance` | 놓치면 실격·감점으로 직결되는 조건. 평가 / 제출 / 분량 / 자격 / 준수 5종으로 분류하고 `critical` 표시 |
| `keywords` | 반복 등장하는 핵심어. 평가 기준이나 요구사항에 나온 말은 `weighted`(제안서에서 반드시 받아써야 하는 어휘) |
| `focus` | 평가 항목별 배점 · 비중(%) · 근거가 되는 요구사항. 분량 제한이 있으면 배점 비율로 나눈 권장 페이지까지 |
| `background` | 사업 배경·목적 문단. 고객의 의도를 읽을 수 있는 유일한 서술 |
| `totalScore` · `pageLimit` | 총 배점, 본문 분량 제한 |

`components/StrategyBriefSection.tsx`가 이를 분석 화면에 함께 보여줍니다.

</br>

### 4. Win Theme 선택 (`lib/rfp/winTheme.ts` · `components/WinThemeStep.tsx`)

Win Theme은 **"왜 우리가 이 프로젝트를 해야 하는가"에 대한 한 줄 답변**입니다.

`buildWinThemes()`가 브리프를 읽어 최대 6가지 방향을 제시합니다: 최고 배점 집중 / 오픈 이후의 안정성 /
감사까지 통과하는 보안 / 단절 없는 기존 업무 연계 / 과락 없는 기술 완성도 / 요구사항 전수 대응.
각 방향은 한 줄 선언과 함께 **RFP에서 찾아낸 근거**(배경 · 평가 · 요구사항 · 조건)를 달고 나옵니다.
해당 근거가 RFP에 없으면 그 방향은 제시되지 않습니다.

사용자는 방향을 고르고, 선언 문장을 **직접 수정**할 수 있습니다.

</br>

### 5. 분석 결과 확인 (`components/RfpAnalysis.tsx`)

추출된 사업 개요 / 요구사항 / 평가 기준을 페이지 번호와 함께 보여줍니다. 요구사항은 기본적으로 전부
선택돼 있고, 오탐을 체크 해제하면 제안서에서 빠집니다. 규칙 기반이라 누락·오탐이 있을 수 있으므로
화면에서 원문과 대조하도록 안내합니다.

</br>

### 6. 제안사 정보 입력 (`components/ProposerForm.tsx`)

사용자가 입력하는 **유일한** 영역입니다.

| 항목 | 필수 | 반영되는 곳 |
|------|:---:|------|
| 제안사 (우리 회사) | ● | 표지, 조직도, 마무리 슬라이드 |
| 작성자 · 작성일 | | 표지, 다음 단계 슬라이드의 연락처 |
| 회사 소개 | | 제안사 소개 슬라이드 |
| 핵심 역량 | | 제안사 소개 슬라이드 |
| 주요 수행 실적 | | 수행 실적 슬라이드 (비우면 슬라이드 자체가 생략됨, 최대 6건) |
| 브랜드 로고 | | 표지 이미지 + **제안서 전체 색상** |

화면 상단에는 "RFP에서 자동 반영된 내용"이 읽기 전용으로 표시되어, 입력하지 않아도 제안서에 들어가는
항목을 확인할 수 있습니다.

</br>

### 7. 브랜드 색상 추출 (`lib/brandColor.ts` · `components/BrandLogoSection.tsx`)

로고를 올리면 **브라우저에서** 색을 분석해 제안서 팔레트를 만듭니다. RFP PDF와 같은 원칙으로,
이미지 분석은 서버로 보내지 않습니다.

**추출.** 캔버스에 160px(`SAMPLE_SIZE`)로 축소해 픽셀을 훑고, 투명(α<128)·흰색(휘도>242)·검정(<16)을
버립니다. 로고의 배경과 테두리는 브랜드색이 아니기 때문입니다. 남은 픽셀을 5비트 버킷(`>> 3`)으로 묶은 뒤
`개수 × (0.3 + 채도)`로 순위를 매깁니다. **면적만 보면 무채색 배경이 이기므로 채도에 가중치**를 줍니다.
서로 충분히 다른 색만 최대 6개(`MAX_COLORS`) 남기고, 사용자가 그중 대표색을 고릅니다.

**파생.** `buildPalette()`가 대표색 하나에서 `BrandPalette`의 11개 토큰을 만듭니다
(`brand` / `brandDeep` / `brandDark` / `brandMid` / `brandPale` / `paper` / `ink` / `gray` / `line` /
`band` / `white`). 밝은 색일수록 더 많이 어둡게 섞어 대비를 확보합니다. 노랑 `#FFD400`도 제목색이
`#695908`이 되어 흰 배경에서 읽힙니다.

로고를 넣지 않으면 `DEFAULT_BRAND`(앱 UI와 같은 오렌지 `#EA580C`)가 쓰입니다.

</br>

### 8. PPTX 생성 (`lib/generatePptx.ts`)

`app/api/generate/route.ts`가 서버에서 `generateProposalPptx()`를 호출해 `.pptx`를 스트리밍합니다.
PowerPoint가 시스템에 설치된 한글 폰트를 사용하므로 폰트 파일을 임베드하지 않습니다.

팔레트는 **모듈 상수가 아니라 인자**로 슬라이드 빌더에 전달됩니다. 요청마다 색이 달라져야 하고,
공유 상수를 쓰면 동시 요청이 서로의 색을 덮어쓰기 때문입니다.

</br>

## 생성되는 발표자료 구조

16:9 비율, **최대 35장**. 근거가 없는 장은 자동으로 생략됩니다.

### Win Theme은 반복하지 않고 뼈대로 씁니다

확정된 Win Theme 문장을 매 장에 되풀이하지 않습니다. 대신 문서 전체를 **하나의 논지**로 묶고,
각 장이 그 논지의 어느 단계인지를 eyebrow에 밝힙니다.

```
판단 기준  →  그래서 무엇으로 판단해야 하는지 밝힌다
문제 정의  →  발주기관이 무엇을 겪고 있는지 확인한다
충족 근거  →  그 기준을 어떻게 충족하는지 증명한다
실행 역량  →  약속을 지킬 수 있는 조직과 계획을 보인다
```

각 단계 앞에 간지가 들어가고, 요구사항 대응 표는 **Win Theme의 근거로 인용된 항목을 앞으로 당겨**
정렬합니다.

</br>

박아두면 05 없는 06이 나오기 때문입니다. 각 장은 조기 반환을 통과한 뒤에 번호를 받아 가므로,
빠진 장은 자리도 남기지 않습니다.

> 평가 상세(곁번호) 때문에 본문 eyebrow와 반드시 어긋납니다.

### 일정은 RFP의 사업 기간에서 나옵니다

단계 구성(Phase 1~4)은 표준안이지만 **길이는 RFP가 적은 사업 기간에서 끌어옵니다**(`schedulePhases()`).
`6개월` → 24주, `3개월` → 12주로 환산해 단계 경계를 비율로 나눕니다. 읽어내지 못하는 문구
(`별도 협의`)나 비상식적인 값은 표준 24주로 되돌리고, 각주 문구가 그에 맞게 달라집니다.

추진 일정 표 · 간트 · 산출물 세 장이 **같은 배열을 보므로** 서로 어긋날 수 없습니다.

</br>

### 수치의 출처

사용자가 입력하는 것은 제안사 정보뿐이고, 사업에 관한 내용은 전부 `data.rfp`에서 나옵니다.
근거가 없는 수치는 문서에 넣지 않는다는 것이 이 도구의 기본 규칙입니다.

| 항목 | 출처 | 근거가 없을 때 |
|------|------|------|
| 사업 예산 · 가격 평가 배점 | `rfp.budget`, `rfp.evaluations` | 비용 장 전체 생략 |
| 비목별 금액 | 없음 | 비목의 포함 범위만 적고, 금액은 산출내역서로 넘김 |
| 기대 효과 목표값 | 요구사항 원문에서 정규식으로 추출, 행마다 근거 페이지 표기 | 장 전체 생략 |
| 단계 기간 | `rfp.duration`을 주 단위로 환산 | 표준 24주, 각주에 표준임을 명시 |
| 투입 인원 · 등급 | 없음 | 조직도에 역할만 표기, 착수 시 확정한다고 각주 표기 |
| 일정 · 날짜 | 없음(`RfpSource`에 필드 없음) | 다음 단계 슬라이드는 절차만 표기 |
| 하자보수 기간 | 없음 | "계약에 정한 기간"으로 표기 |

표준 서술에 기대는 장(조직 · 산출물 · 유지보수)은 각주에 그것이 표준임을 밝힙니다.
사업 개요처럼 값을 못 찾은 항목은 `제안요청서 미명시`로 적습니다.

</br>

### RFP가 실제로 꺼낸 말에만 반응합니다

리스크 · 품질 활동은 어느 사업에나 있는 기본 항목을 깔고, **요구사항 원문에 해당 낱말이 있을 때만**
항목을 더합니다.

| 트리거 | 리스크 | 품질 활동 |
|------|------|------|
| 연계 · 연동 · 인터페이스 · API | 외부 시스템 연계 실패 | 연계 시험 |
| 이관 · 마이그레이션 · 전환 | 데이터 이관 오류 | |
| 개인정보 · 보안 · 암호화 | 보안 요건 미충족 | 보안 취약점 점검 |
| 성능 · 응답 · 처리량 · 가용성 | | 성능 시험 |

해당 낱말이 없는 RFP에서는 그 항목이 표에 나타나지 않습니다.

</br>

### 요구사항 "대응 방안"은 자동 생성 문구입니다

사용자가 대응 방안을 직접 입력하지 않는 구조입니다. `RESPONSE_RULES`의 **13가지 주제별 규칙**
(연계·이관 / 보안 / 성능·가용성 / 데이터·분석 / 관리기능 / 자동화 / 화면 / 교육 / 법규 / 인프라 /
품질 / 일정 …)이 요구사항 문장에서 실제로 등장한 낱말을 집어 문구에 되돌려 넣고, 어느 것에도 걸리지
않으면 유형별 기본 문구(`STANDARD_RESPONSE`, 기능 / 비기능 / 기타 3종)를 씁니다.

매칭은 **공백을 지운 문자열**에 대고 합니다. PDF에서 뽑은 문장은 `자동라우팅기능`처럼 띄어쓰기가
뭉개져 있어 그대로는 걸리지 않습니다.

> 그래도 자동 생성 문구입니다. **실제 제안서로 제출하려면 PowerPoint에서 각 요구사항에 맞게
> 보완해야 합니다.**

</br>

### 줄표를 쓰지 않습니다

생성물에 줄표 계열 문자(U+2014, U+2013, U+2015, U+2012)를 넣지 않습니다. 한국어 실무 문서에서
쓰지 않는 기호이므로, 쉼표나 쉼표 뒤 문장 분리로 대체합니다.

`newSlide()`가 슬라이드의 `addText` · `addTable`을 감싸 텍스트를 지나가며 치환하므로, 개별
슬라이드 함수는 이를 신경 쓰지 않아도 됩니다. 치환 뒤 생기는 `,,` `,.` 같은 자국까지 정리합니다.
가운뎃점(`·`)은 한국어 문서에서 정상이므로 그대로 둡니다.

> **주의:** `addChart`는 이 래퍼를 타지 않습니다. 차트 라벨에는 치환 함수를 직접 적용해야 합니다.

</br>

## 기술 스택

- **Frontend/Backend**: Next.js 14 (App Router), TypeScript, React
- **스타일링**: Tailwind CSS (Orange · Black · White 디자인 시스템)

### 디자인 시스템

오렌지가 **유일한 채색**이고 구조는 검정과 흰색이 담당합니다. `tailwind.config.ts`의
`accent.green` / `amber` / `red`도 전부 오렌지(`#EA580C`)로 통일돼 있어 상태색이 따로 없습니다.

섹션 헤더는 검정 바(`bg-ink-900`)라 그 위 텍스트는 반드시 `globals.css`의
**`.fs-title` / `.fs-desc` / `.fs-index`** 를 써야 합니다. 일반 `text-ink-900`을 쓰면 검정 위 검정이
되어 보이지 않습니다. 배지도 `.badge-accent` / `.badge-neutral` / `.badge-muted`를 씁니다.

## 개발 시 참고 사항

### pdf.worker.min.mjs 버전 동기화

`pdfjs-dist`는 파싱을 별도 Worker 스크립트로 실행하며, `public/pdf.worker.min.mjs`는
`node_modules/pdfjs-dist/build/pdf.worker.min.mjs`를 그대로 복사해 커밋해 둔 파일입니다.

**`pdfjs-dist`를 업그레이드하면 이 파일을 반드시 수동으로 재복사해야 합니다.**
버전이 어긋나면(`API version X, Worker version Y`) 브라우저 콘솔에 에러가 나며 PDF 파싱이 실패합니다.

```bash
npm install pdfjs-dist@latest
cp node_modules/pdfjs-dist/build/pdf.worker.min.mjs public/pdf.worker.min.mjs
```

</br>

### CSS는 JSX의 `<style>` 태그에 넣지 마세요

`<style>{`...`}</style>` 안에 큰따옴표가 들어가면 **서버는 `&quot;`로, 클라이언트는 `"`로**
직렬화해 hydration이 실패합니다. 주석 안의 따옴표 하나로도 화면 전체가 깨질 수 있습니다.

컴포넌트 전용 CSS는 `HomeHero.css`처럼 별도 파일로 만들어 `import`하세요.

</br>

### 스캔 PDF는 지원하지 않습니다

OCR을 쓰지 않으므로 이미지로만 이루어진 PDF에서는 텍스트를 추출할 수 없습니다.
업로드 화면에 안내가 표시됩니다.

</br>

### PPTX 레이아웃 수정 시

`lib/generatePptx.ts`의 좌표 단위는 **인치**입니다(16:9 = 10 × 5.625). `MARGIN`과 `BODY_W` 상수를
기준으로 배치하면 좌우 여백이 맞습니다. 표의 `colW` 합계는 `BODY_W`를 넘지 않아야 하며, 넘으면
슬라이드 밖으로 밀려납니다.

주의할 점:

- **새 슬라이드는 반드시 `newSlide()`로 만드세요.** `pptx.addSlide()`를 직접 부르면 줄표 제거가
  걸리지 않습니다.
- 색은 `pal.xxx`에서만 가져오세요. 하드코딩한 hex는 로고 색을 무시합니다.
- pptxgenjs의 색은 `#` 없는 6자리입니다. 8자리(알파 포함)를 넣으면 **파일이 손상됩니다.**
- 표에는 `autoPage: false`를 주세요. 자동 페이지 분할이 레이아웃을 깨뜨립니다.
- **세로 여백을 계산하고 넣으세요.** 넘치는 요소는 슬라이드 밖으로 밀려나며 아무 에러도 나지
  않습니다. 목차는 항목 수에 따라 두 단으로 나누어 이를 피합니다.
- 요구사항이 많으면 `ROWS_PER_SLIDE`(현재 **4**)로 나눠 담습니다. 표 행 높이를 키우면 이 값도
  함께 줄여야 합니다.

</br>

### 빌드하면 dev 서버가 깨집니다

`npm run dev`가 떠 있는 상태에서 `npm run build`를 돌리면 `.next`를 덮어써서 실행 중인 dev 서버가
`Cannot find module './###.js'`로 500을 냅니다. 순서대로 복구하세요.

```bash
# dev 서버 종료 후
rm -rf .next
npm run dev
```
